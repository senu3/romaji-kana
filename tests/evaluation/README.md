# 変換品質評価セット（草案 v0.2）

このセットは、実際のローカルモデルやプロンプトを比較するための手動評価用データです。44件・8分類で、読みの忠実さ、自然さ、不要な補完、辞書・保護語、補完差分の信頼性を確認します。追加した12件はOllamaのgemma4:latestで各1回ずつ確認しました。全44件の反復評価と正式な採点は未実施で、採点基準も暫定です。

既存の単体テストは処理の契約と回帰を検証します。このセットは生成結果の品質を評価するものであり、単体テストを置き換えません。実行ランナーは出力収集と速度の集計を自動化します。意味や自然さの採点は人が行います。

## 実行方法

現在の標準は `--engine hybrid`（Rust辞書候補＋LLMの選択）。`--engine llm` で従来のLLM生成、`--engine local` で辞書のみを比較できる。localは通常変換のケースに限り、モデル指定は不要。修正・補完・推測のケースをlocalへ渡すと実行前にエラーにする。

```sh
npm run eval:run -- --engine local --case basic-01,basic-02 --repeats 1
npm run eval:run -- --engine hybrid --model YOUR_MODEL --case basic-01,basic-02
npm run eval:run -- --engine llm --model YOUR_MODEL --case basic-01,basic-02
```

manifestには方式と辞書リビジョン・ファイルハッシュも保存する。trialの `engineCalls` に辞書要求と応答、`apiCalls` にモデル通信を別々に保存する。`exactReferenceMatch.top` と `pool` は許容例への完全一致を数える補助指標で、人手による正解判定・品質合格率ではない。複数の正解表記があり得るため、不一致を誤変換と断定しない。

再順位付けが失敗してローカル候補へ戻った場合でも、モデル通信の失敗はログに残す。タイムアウト後の処理がサーバーに残る可能性があるため、評価ランナーは通信失敗時に次のケースへ進まない。Rustプロセスのビルド・初回読込を含むため、初回はウォームアップとして測定外にする。

リポジトリ直下で実行します。既存のNode.js・Viteを使い、追加パッケージは不要です。

```sh
# データと実行順の確認のみ。モデルへの通信なし
npm run eval:run -- --dry-run

# --model はサーバーにある実際の識別子に置き換える
npm run eval:run -- --provider ollama --model YOUR_MODEL
npm run eval:run -- --provider lmstudio --model YOUR_MODEL --url http://localhost:1234

# 少数例での疎通・別プロンプトの比較
npm run eval:run -- --model YOUR_MODEL --case basic-01,basic-02 --repeats 1
npm run eval:run -- --model YOUR_MODEL --prompt ./candidate-prompt.txt --seed 20260922 --note "比較条件の説明"

# ランナーの検証。実モデルは使用しない
npm run eval:test
```

保存先は標準で `tests/evaluation/results/<日時と識別子>/` です。`--out` で変更できますが、既存ディレクトリへの上書きは拒否します。結果ディレクトリはGitの追跡対象外です。

- `manifest.json`：評価データのハッシュ、Git状態、環境、全設定・プロンプト、ケース、実行順。dry-runでも保存する。
- `trials.jsonl`：1行1試行。最終戻り値、実HTTPリクエスト・応答、時間、呼び出し回数、人手採点用の `review` 欄。
- `summary.json`：分類別の候補数・棄却数・空結果数・エラー数と所要時間の中央値。品質合格率ではない。

棄却の詳細は結果の `rejectionDetail`、応答形式の例外は `errorDiagnostic` に記録します。既存の大分類 `suggestionRejectedReason` は互換性のため維持します。

各実行は先頭ケースで1回ウォームアップし、指定された全ケースを標準3回ずつ逐次実行します。ウォームアップはJSONLに残しますが集計から除きます。モデル読込状態は検出していないので、初回計測をコールドスタートと断定しません。既定シードと同じケース集合・繰り返し数で実行順を再現できます。プロバイダー間の実行順交替は実験者が行います。

通信にはアプリのブラウザー用transportをそのまま使います。Tauri固有の通信経路の検証ではありません。HTTP応答本文の読取りを含む計測で、ログ用の複製・収集にも小さなオーバーヘッドがあります。通信エラーでは直ちに停止して記録を保存し、終了コード1を返します。タイムアウト後にサーバーで生成が続く可能性があるため、自動で次のケースへ進みません。途中再開は未対応です。

`review` の点数・重大失敗・差分誤表示・利用可能判定は初期値が `null` です。READMEの採点基準に沿って記入し、未評価を0点や合格として集計しないでください。レビュー記入後の品質集計は現時点では手動です。API応答の生データは保存しますが、合格文字列への自動照合はしません。

GPU、量子化、サーバー版など自動取得しない情報は `unknown` とし、取得できた条件は `--note` へ追記してください。認証付きエンドポイントの設定は未対応です。プロンプトや応答を保存するため、共有前にその内容を確認してください。

## 対象とデータ

[cases.json](./cases.json) の各ケースを、公開関数 `convertRomajiToJapaneseDetailed(input, settings, transport, options)` に渡す想定です（[実装](../../src/lib/ollama.ts)）。モデルに直接プロンプトだけを送らず、かな化・保護語分割・補完検証・再試行を含むアプリの変換全体を測ります。

| 分類 | 件数 | 主な確認点 |
| --- | ---: | --- |
| basic | 4 | 普通の文章、助詞、促音、口調 |
| reading | 7 | 同音異義語、入力内・分割前方の文脈、ローマ字表記の揺れ |
| meaning | 4 | 否定、未決定、推量、過去時制 |
| protected | 6 | 時刻、金額、リテラル、既存の漢字、数字の発音と助数詞 |
| dictionary | 4 | 連続入力、短い読みの誤一致、リテラル優先、無効項目 |
| vocabulary | 4 | 同音の表記参考、無関係な語彙、命令混入、文脈との衝突 |
| word | 11 | 末尾の単語補完、語尾・複合語の完成、局所修正との併用、不要な追加 |
| sentence | 4 | 簡潔な文章化、意味・否定・数字の維持 |

各ケースのフィールドは次の意味です。

- `id`：結果との照合に使う固定ID。内容変更時は評価セットの版も更新する。
- `input`：変換範囲の入力。文書全体や説明文は付け足さない。
- `settingsOverrides`：そのケースだけの `AppSettings` 上書き。辞書配列は置き換える。
- `options`：そのケースだけの `JapaneseConversionOptions`。文書語彙はここに渡す。
- `acceptableExamples`：許容例であり、網羅的な正解文字列ではない。単純な完全一致で合否を決めない。
- `criteria`：人が確認する条件。漢字・かなの自然な表記揺れは許容する。
- `criticalChecks`：破ると重大失敗となる条件。これ以外でも否定反転や事実創作は重大失敗として記録する。
- `notes`：評価者向け補足。モデルへ送らない。

### 設定の組み立て

リポジトリの `defaultSettings` をベースにし、JSONの `defaults`、ケースの `settingsOverrides` の順で適用します。ただし `defaults.documentVocabulary` は設定項目ではなく `options.documentVocabulary` の初期値です。評価対象のプロバイダー・接続先・モデル名・プロンプトは実験条件として指定します。

ケースごとに辞書・オプションを初期化し、前のケースの値を引き継がないでください。語彙のあるケースでは `useDocumentVocabulary: true` とし、指定された語彙だけをオプションに渡します。ここでは文書からの語彙抽出は評価しません。`avoidOutputs`、`completionMode`、`speculativeMode` は通常評価では指定しません。

句読点は標準設定で日本語に変換します。入力中の保護リテラルの囲みバッククォートは、現在の仕様では除去されます。「Markdownのバッククォートを常に残す」という採点をしないでください。

通常変換・提案・別候補から推測へ自動移行しません。ひらがなだけの成功候補も保持します。推測は `speculativeMode: true` の明示要求だけです。結果の `conversionStrategy`、`suggestionRejected`、`changes.readingAssessment` も確認してください。読みが未確認の漢字候補はTab採用に限定され、候補が返ったこと自体は品質合格を意味しません。

## 採点

各試行で、まず「候補あり」「安全な棄却」「通信・処理エラー」を分けて記録します。棄却は危険な候補を防げた結果でも、変換の成功には数えません。空の結果、タイムアウト、入力そのままの返却を、無条件で成功にしないでください。

候補のある試行を次の3軸でそれぞれ0〜2点で採点します。合計点だけで重大な欠陥を相殺しません。

| 軸 | 2点 | 1点 | 0点 |
| --- | --- | --- | --- |
| 忠実さ | 読み・意図・事実を維持 | 解釈に迷うが明確な意味変更なし | 読み違い、意味変更、入力にない事実 |
| 自然さ | そのまま使える | 表記や文章に小修正が必要 | 不自然で使えない |
| モード適合 | 許可された範囲の変更だけ | 境界例で要確認 | 通常変換で言い換え、単語補完で句を追加等 |

文章モードは現行プロンプトが軽い修復・並べ替え・短い続き・同意図の言い換えを許可しています。読みの完全一致を要求せず、中心的意図・口調を評価します。ただし、金額変更、否定反転、入力から裏付けられない具体的事実は許容しないという品質目標を置きます。これは現行コードが意味の安全性を保証しているという説明ではありません。

別枠で次を記録します。

- **重大失敗**：数字・保護語の破壊、否定反転、具体的事実の創作、辞書や語彙に混じる命令の実行。内容と最終結果を残す。
- **追加表示の誤り**：`inputCompletionAdditions` が、元からある文字や実際に追加されていない文字を追加扱いしていないか。漢字化そのものは追加ではない。元入力、補完元かな、結果の読みを照合し、モデル申告だけを根拠にしない。
- **追加表示の省略**：明確な挿入を表示しない場合と、言い換えのため確実な差分を出せず省略した場合を区別する。後者は許容する。
- **推測への移行**：推測候補が有用でも、忠実な通常変換の成功とは別集計にする。採用前に利用者の確認が必要な候補として扱う。

「そのまま利用可能」は3軸すべて2点、重大失敗なし、誤った追加表示なしの候補とします。分母はエラー・棄却を含む全試行です。分類別利用可能率、棄却率、エラー率、重大失敗件数、追加表示誤り件数を併記します。小さなセットなので百分率だけでなく件数も示します。

暫定の採用条件は、重大失敗と誤った追加表示が観測上0件であること、同条件の現行版から分類別の利用可能件数が悪化しないことです。44件で安全性を保証できるわけではありません。判断が割れる例は要レビューとして残し、基準を調整してから比較対象の両方を再採点します。

12件の確認結果と未解決項目は [conversionRoadmap.md](../../src/lib/conversionRoadmap.md) に記録しています。v0.1とv0.2を比較するときは共通のケースIDを使い、追加ケースを含めた集計と混ぜないでください。

## 比較の手順と速度

1. 現行版を基準にし、モデルまたはプロンプトのどちらか一方だけを変更する。プロバイダーを比較する場合も他の差を記録する。
2. モデル読込を含む初回計測と、ウォームアップ後の計測を分離する。初回扱いはサーバー側の読込状態を確認できた場合だけにする。
3. 同じ32件を各条件で3回ずつ逐次実行する。固定して記録した順序シードで順序を入れ替え、比較条件間の実行順も交互にする。並列実行による競合を避ける。
4. 公開関数呼び出し開始から最終結果・エラーまでを測る。修復・分割・再試行の全時間と全API呼び出し回数を含める。利用者の入力待ちタイマーは別測定にする。
5. 結果の条件名を隠して採点し、重大失敗・境界例を再確認する。3回のばらつきを残し、よかった1回だけを採用しない。
6. 分類・モードごとの時間の中央値と件数を出す。全体のp95は参考値とし、少数例の分類別p95から結論を出さない。エラーと外部打ち切りは速度の成功標本から除外し、別件数・経過時間を明記する。

計測のために本番の通信パラメーターや再試行条件を変えないでください。外部の実行時間上限を設ける場合は値を記録し、打ち切り後もサーバーの生成が続いていないか確認してから次へ進みます。クライアント側のキャンセルがサーバー計算の停止を保証するとは限りません。

### 結果に残す項目

| 単位 | 記録項目 |
| --- | --- |
| 実験 | 評価セット版、Git SHAと未コミット差分の有無、日時、OS、CPU/GPU/RAM/VRAM、プロバイダーとサーバー版、モデル識別子・量子化・ダイジェスト（取得可能なら）、プロンプト本文またはハッシュと参照先、全設定、実行順・シード、初回/ウォーム状態 |
| 試行 | case ID、繰り返し番号、実際の入力・設定・オプション、戻り値全体、エラー、全体時間、API呼び出し回数、各呼び出しの時間と状態、採点、重大失敗と差分表示の判定理由 |

結果は実験ごとのJSONLに保存します。認証情報を記録せず、モデル識別情報が取得できない場合は推定せず「不明」とします。実モデルでの実行結果はまだ作成していません。

## API・編集操作の別枠チェック

以下は文章の品質点に混ぜず、モックまたはアプリ上のシナリオで検証します。既存テストの該当範囲を再利用し、不足する部分を追加するためのチェックリストです。今回この表を作ったことは実行・合格を意味しません。

| シナリオ | 期待する確認内容 | 主な方法 |
| --- | --- | --- |
| 差分申告の偽り | 既存のかなを `additions` に申告させても、虚偽の追加表示にしない。真の挿入は検出する | 変換レスポンスのモック |
| 言い換えの差分 | 文章提案で削除・並べ替えを含むとき、確実でない追加表示を出さない | 変換モックと表示確認 |
| 通信契約 | OllamaとLM Studioそれぞれのパス・本文・応答抽出が正しい。内部処理用の情報を誤って通信項目に混ぜない | transportの契約テスト、対応サーバーで疎通 |
| 互換オプションの再試行 | thinking/reasoningの非対応応答だけで互換再試行する。モデル未検出や503を誤判定しない | HTTP状態とエラー本文のモック |
| 変換中の文書差し替え | 遅れた変換結果が別文書へ適用されない | 遅延Promiseとフックテスト |
| キャンセル後の応答 | 遅れた応答で本文・候補・履歴を更新しない | AbortSignalと遅延Promise |
| 候補の陳腐化 | 入力変更後の古い候補を採用できない。推測候補の採用操作も確認する | フックテスト、エディター操作 |
| 保存中の編集 | 保存開始後の編集を保存済み扱いしない | 保存APIの遅延モック |
| スマホ同期 | 受信を送り返さない。古いポーリング結果で新しい編集を上書きしない | 同期APIの遅延・失敗モック、実機 |
| タイマー終了 | アンマウント後に変換・保存・同期が走らない | 偽タイマーとクリーンアップ確認 |
| Markdown範囲 | 見出し・リスト・コードフェンス・リンクを含む文書で変換範囲が適切 | 範囲抽出テスト、エディター操作 |

デスクトップのファイル保存、スマホとの実通信、プロバイダー実サーバーへの疎通は実環境で別途確認し、未実施ならそのまま明記します。

## 次版で増やす例

まずこの草案を人手で読み合わせ、許容例と採点の境界を確定します。その後、本人が実際に困った誤変換を匿名化して追加します。長文、タイプミス、途中入力、記号、複数の辞書語、別候補の探索は今回のカバーが薄い領域です。

プロンプト中の例や既存テストと近いケースは回帰確認には有効ですが、未知の文章への性能を過大評価し得ます。調整用のセットと、プロンプト調整に使わない保留セットを分け、保留セットを見て調整した場合は新しい保留例を用意してください。
